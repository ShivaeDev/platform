# Work Fleet roadmap

## Built

- PostgreSQL tests use effect-test-sql with the Fleet migrations prepared once per worker fixture. Ordinary storage and engine tests roll back; concurrent storage, migration and daemon/process scenarios use clones for real commits. `src/storage/fixtureIsolation.spec.ts` covers Fleet records, reservations and scope-finalizer rollback, and commits visible through a second connection without changing the shared fixture.

- The daemon follows commit-bound effect-sql hints instead of polling PostgreSQL. Record and foreign-occupancy writes use `transact`. PostgreSQL and HTTP tests prove daemon command delivery to a CLI follower, idle-query silence, rollback silence, bounded read recovery and reconnect resync; client subprocess fixtures reject direct PostgreSQL connections.
- Fleet's daemon runs through Platform's `appHost` with its existing RPC path and loopback policy. `appDatabase` runs the shared Fleet migration loader against the namespace ledger before services, retaining the configured pool limit. PostgreSQL and real HTTP tests in `src/host/daemon.test.ts`, `modelMigration.spec.ts`, `migrationStartup.spec.ts`, `daemonClients.spec.ts` and `daemonCommit.spec.ts` cover scope lifetime, populated-record upgrades, migration failure before provider acquisition, client commands, follower restart and commit hints.
- Every Fleet client command uses local HTTP RPC without client PostgreSQL connections. Item-based `answer` records worker text, retry or release answers through the daemon, then resolves them under existing runtime policy. It registers republished decisions against their current template; ready PRs accept requested changes on the same branch and PR. PostgreSQL command tests cover response acknowledgements and shared pool reuse. The followers subscribe before their initial snapshot and resync after reconnect while retaining their selected set and output. HTTP and PostgreSQL regressions cover command output, exit codes, explicit dispatch, daemon restart and missing-daemon errors.

- The local daemon shares one bounded PostgreSQL pool and provider connection set between scheduling and native HTTP RPC. Platform request tracing supplies per-call request ids. PostgreSQL and HTTP regressions cover completion, concurrent clients, resource closure and launch recovery after SIGKILL with a synthetic Cloud backend.

- Cloud threads carry their prepared Board work ID and first heading, with configurable prefixes, trimmed titles, and role labels for separate review and repair threads. `work-fleet name-threads` backfills current and archived sessions, reports failures and skips successful names on repeat runs. Formatting tests and PostgreSQL CLI tests against a synthetic Cloud backend cover naming and idempotence.
- The CLI host atomically publishes a versioned health snapshot for Board Diagnostics. Filesystem, provider and PostgreSQL tests cover freshness, configured capacity, execution counts, waiting counts per owner, scheduler passes and structured provider rejection observations.
- The `work-fleet` command loads `fleet.config.json`, schedules approved Board work with `serve`, explicitly dispatches an item, reports stored views with `status`, and observes outcomes with `wait` for one item or `watch` for several. Host tests cover admission and revision approval against PostgreSQL; CLI tests cover status flags, wait process exit codes and watch outcomes.
- The CLI host publishes an optional `fleet/status.md` heading board with Active, Waiting on maintainer, Waiting on orchestrator, Waiting on automation and Done columns for Work Board. Renderer, filesystem and PostgreSQL scheduler tests cover card grouping, links, unsafe Markdown inputs, authored-content and symlink boundaries, and publication retry.
- Board frontmatter uses `fleet: approved` and per-field `fleet-launch` overrides. Host launch defaults and task overrides reach worker sessions and turns; repair retains the settings. Frontmatter, host and launch-setting tests cover these boundaries.
- The Codex Cloud provider sends the configured environment and launch settings, confirms the environment before a turn and rejects work prepared for a different workspace, reads final output, and refreshes expired login files through a configured command. `src/providers/codexCloud.test.ts` covers these requests and failures with a synthetic WebSocket backend.
- Worker instructions include Cloud startup waiting, current-main checkout, repository checks and one human-review pull request. The report parser recognizes a URL or explicit no-change marker. `src/prompt/worker.test.ts` covers these instructions and parsing.
- Fleet persistence uses effect-sql model repositories with optimistic concurrency for records and model CRUD for foreign occupancy. PostgreSQL migration tests preserve populated JSONB records, versions, admission order and reservations, then exercise updates and requeueing. The daemon migration fixture reads preserved records and writes new work over HTTP. Advisory admission locks and sequence allocation remain explicit SQL because repositories do not expose those operations.
- The Effect core stores preparation, attempts, receipts, review/check evidence, decisions and accepted outcomes in PostgreSQL. Native RPC and owner-grouped waiting views, revision-bound completion, repair, dependency acceptance, renewal and recovery are exercised by the engine tests. Tasks with disjoint areas can dispatch concurrently; occupied areas wait on automation and dependency qualification waits on the orchestrator. PostgreSQL scheduling tests cover admission order, area release and those owner groups; admission tests cover capacity, quota and backlog separately.
- Review launches independent provider sessions through the shared session service and durable journal, using host launch settings and the task, criteria and exact adopted result. Completed machine-readable verdicts record evidence and findings against the exact head. Reviewer and recovery regressions cover asynchronous approval, terminal failure, lost acknowledgement, restart and a head moving during review. Synthetic Cloud and local protocol tests verify read-only execution with network reads and no escalation; live Cloud review remains unproven.
- Managed Board decisions retain exact question/context receipts. Release accepts changed or moved task revisions without requiring current approval. Retry prepares the current approved brief or continues the existing worker with changed criteria; bulk CLI release records closing responses for done and deferred tasks. PostgreSQL and Board HTTP regressions prove concurrent retry, restart recovery and Inbox closure. Current guided retry/release responses resolve idempotently in SQL, and immutable Board request receipts acknowledge applied or superseded decisions. HTTP and renewal tests cover publication recovery and stale or ambiguous responses.
- Completed worker and repair turns that report the explicit `FLEET_QUESTION:` marker publish ordinary Board questions. A current answer commits a response receipt and continuation intent together, then continues the same worker thread; concurrent resolution, restart and lost acknowledgements reconcile the existing operation without repeated submission. Open questions return the CLI's waiting exit code and name the next actor. Routine questions default to the orchestrator; an explicit maintainer marker or reassignment routes them to the maintainer. PostgreSQL and RPC tests cover durable owner routing, reassignment, publication recovery and rejection of superseded answers. Upgrade tests preserve maintainer routing and adopt answers recorded before migration. Reassignment recovery tests retry the original decision ID and force a race with resolution, proving a typed stale failure for the losing write. The worker-question and continuation tests cover these boundaries.
- The command host reads GitHub check runs and commit statuses for the adopted PR's exact SHA through `gh`. Pending checks keep validation open and failures reach repair. `src/host/githubChecks.test.ts` and `src/engine/validation.spec.ts` cover these transitions with synthetic GitHub responses.
- Approved tasks with `fleet-deliverable: report` return the whole report in the worker's final message. Fleet records an immutable Board result with the task relationship and exact session/turn provenance, then completes without PR adoption, review, checks or delivery; empty output waits on the orchestrator. PostgreSQL and Markdown host regressions cover completion, empty output, status, wait and lost-publication recovery without a duplicate result or worker.
- The CLI host reconstructs report attachments from the completed turn’s paginated app-server file changes, restricted to `/tmp/fleet-report/attachments/`. Prompts require file-edit tools and declare every promised file; adds, updates, moves and deletes replay in order. Unavailable retrieval and replay collection limits publish report text with unavailable-file records. Local attachment validation and saved-payload failures park the completed attempt with the file path and cause; PostgreSQL `src/engine/reportFileFailures.spec.ts` covers those reasons. A durable publication payload preserves text, attachment bytes and warnings across restart and lost acknowledgements without recollection; `src/host/reportBoard.test.ts`, `src/board/reportPayloadFile.test.ts` and PostgreSQL `src/engine/reportRecovery.spec.ts` cover changing retrieval outcomes. Synthetic WebSocket, replay, filesystem and PostgreSQL regressions cover retrieval, publication, size limits, immutable storage and refusal of public worker branches or PRs. Hosted file-change exposure was observed in a maintainer-run Cloud probe; live report completion and published attachment bytes still need verification through the rewritten collector.
- The Cloud adapter and headless host commit each attempt intent before `thread/start`, the session acknowledgement before `turn/start` and the turn acknowledgement before observation. PostgreSQL SIGKILL tests with a synthetic Cloud server cover both sides of these mutations and recovery of 100 concurrent attempts with lost turn acknowledgements. An acknowledged Cloud thread that stays empty through a five-second grace period receives its saved turn on the same thread and attempt; late accepted turns are adopted. SIGKILL regressions cover empty-thread recovery and guided retry of a legacy missing-turn decision. Retry and release retire intents without a persisted session acknowledgement through a compare-and-set write that fences late acknowledgements before any turn can start. Ambiguous duplicate terminal turns retain every matching receipt across all pages in `SessionFailure.terminalReceipts` and the persisted attempt. Release verifies each exact receipt and confirms every turn is terminal; running, unavailable or mismatched evidence retains ownership. `src/engine/unacknowledgedIntent.spec.ts` and `src/engine/terminalReceipts.spec.ts` cover restart, repeated responses, late acknowledgements, fresh retry and safe release with real PostgreSQL and the native adapter over synthetic provider responses.
- Fleet never submits a merge. Reviewed, green PRs wait on the maintainer; the command host observes the adopted PR through `gh pr view`, accepts only a merge of the reviewed head, keeps closed unmerged PRs waiting on the orchestrator and preserves the current decision through transient observation failures. Delivery tests cover these cases with synthetic GitHub responses and real PostgreSQL.
- The local Codex adapter connects to an independently owned app-server. `src/providers/codexLocal.test.ts` covers receipts, reconnect, explicit interruption and observation-scope closure with a synthetic backend.

The host can select GitHub result adoption with `result: "github"`. Synthetic GitHub responses prove final-marker placement with whitespace and backtick tolerance, exact reported-head checks, open or merged PR identity, paginated paths and observation-race rejection. PostgreSQL fixtures persist the adopted PR number, head and paths, route failed adoption to the orchestrator, and require terminal independent review and checks before accepting a reported no-change result, preserve that result when main moves and reject a changed task revision. `src/engine/mergedAdoption.spec.ts`, `src/engine/mergedReview.spec.ts` and `src/engine/mergedReviewRecovery.spec.ts` use real PostgreSQL and a synthetic HTTP GitHub server to cover merges before adoption or during review, mismatched merged heads, unmerged closures and retries from stored decisions without repeating worker execution or an existing review. Live GitHub adoption remains pilot evidence.

## Open for the command host

For the opt-in GitHub adapter, the result-adoption item below requires live pilot evidence.

- Result adoption: verify and attach the actual pull request or evidenced no-change result. A worker report marker alone is insufficient.
- Board view: present Fleet execution attachments and decisions in the Board interface.

The command host's default integrations read GitHub checks and observe human delivery of the adopted PR, and the engine runs independent reviewer sessions, but the host does not supply result adoption. The PostgreSQL host-loop test waits on automation after a terminal worker when adoption is unavailable. Pending checks also wait on automation. Reviewed, green PRs wait on the maintainer to merge. Completion tests use injected synthetic integrations; they prove the core path, not these open host integrations.

## Validation boundary

Real PostgreSQL tests cover durable storage, host admission, status reads, wait process behavior and engine transitions. Board HTTP tests exercise response and acknowledgement publication. Synthetic paginated GitHub responses cover green, red, pending and newer-push checks; they do not prove live GitHub authentication or branch requirements. Cloud and local provider tests use synthetic WebSocket servers. Status board tests include invalidation of a mounted native Board page over real HTTP; they do not establish physical-browser acceptance. Packed consumers exercise the package exports and command help.

The daemon's `daemon.diagnostics` HTTP RPC query serves in-memory Fleet health and cached Codex/GitHub rate-limit observations to Board. `src/host/boardDiagnostics.spec.ts` exercises the real daemon and Board over HTTP against PostgreSQL, covering owner counts and health reads without a health file. Board's HTTP fixtures cover a stopped daemon, reconnect and stale health observations. The CLI host publishes an atomic versioned `fleet/health.json` using Board's shared schema. Filesystem fixtures cover atomic replacement, unchanged writes, authored content and symlink refusal; restart fixtures restore last scheduler/capacity observations. PostgreSQL scheduler fixtures exercise actual Fleet counts and independent status/health publication, while synthetic provider fixtures cover structured capacity errors across the WebSocket boundary and terminal-turn observation. These checks live in `src/board/writeHealth.test.ts`, `src/host/healthLayer.test.ts`, `healthPublication.spec.ts`, `providerHealth.test.ts`, and `src/providers/capacityWire.spec.ts`. They do not establish live provider capacity or credential access.

Live Cloud computation, actual pull request adoption, independent review, required checks and an observed human merge still need end-to-end evidence. A terminal turn, a report URL and accepted delivery are separate facts. No synthetic fixture supplies live proof.

## Maintainer decisions

- Release and public distribution: the package remains private at version `0.0.0`.
- Live pilot: validate disjoint work, replacement timing, restart recovery and an observed human merge under actual branch requirements once the open host integrations are connected. Live hosted restart evidence remains pending.
