# @shivaedev/work-board

You are changing the local workspace where a person reads their agents' plans, results and questions, inspects the evidence, and gives direction in context. Project Markdown is the work's source of truth; the board makes it understandable without requiring another copy in a task database. A folder of ordinary notes must remain useful before its author adds identity, relationships or responses. Read [the north star](docs/north-star.md) for the full direction, [the roadmap](docs/roadmap.md) for acceptance and maintainer decisions, and [the README](README.md) for authoring and integration.

## Which way to lean

When goals conflict, they win in this order:

1. **The files keep their meaning.** Agents use ordinary file edits. Work Board owns the human response content it records; agents own the surrounding project Markdown. Preserve readable source and reviewed context. Do not require a special agent writer or build universal concurrent-editor transactions.
2. **The reader can trust what is shown.** A recorded claim, completed run, response, handoff receipt, closed request and accepted result are different facts. Pin feedback to reviewed report bytes and path; authored acceptance does not establish criterion evidence. Show missing, ambiguous, stale and unavailable information; never infer a convenient answer.
3. **Reading stays calm and local.** Make the next judgment easy to find, keep its evidence close, and preserve orientation as files change. Quiet work remains quiet. Keep the loopback and explicit write-opt-in boundaries.
4. **One path does each job.** Own Markdown reading, indexing and workspace interactions here. Build on native Effect and Platform contracts, RPC and live primitives; agent tools own execution and editors own project editing.
5. **Structure earns its cost.** Keep plain Markdown and heading boards useful. Add metadata, controls or integrations only for a demonstrated reader need.

Use practical draft retention, revision checks and clear save outcomes. Rare outside-editor races are an accepted best-effort boundary, not permission to hide ordinary failures. The roadmap owns handoff and integration decisions; a passive question wait and a prepared handoff do not launch an agent. Keep ordinary receipt edits separate from execution and acceptance, including in optional integrations.
