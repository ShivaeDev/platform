# Start a Platform app

Use Node 24 or newer and pnpm 12.8.1. The [starter](../../examples/starter) is a private notes app with PostgreSQL, Platform's app host, RPC, shared query state, routing, a form, Vite, React and Tailwind with stock shadcn components.

1. Run `pnpm create @shivaedev/app my-app`, then `cd my-app`. The command writes the starter with exact published Platform versions, keeps its self-contained pnpm catalog, installs dependencies, and generates a git-ignored `.env.local` with a fresh authentication secret and `my_app_dev`/`my_app_test` database URLs. Use an absent or empty folder; existing files are never overwritten.
2. Run `pnpm dev` and open `http://127.0.0.1:5173`. It first runs `pnpm db:setup` to prepare both databases through `@shivaedev/local-postgres`; have local PostgreSQL 18.6 on port 55432 or Docker available. The server and background worker watch TypeScript, Vite serves React, and `pnpm migrate` applies migrations, including Better Auth's tables, before either process starts. Follow the sign-in link, create an account, then add a note. The worker counts each note's words; the count appears without refreshing. Sign out and sign back in to see your saved notes.

Run `pnpm test` to load `TEST_DATABASE_URL` from `.env.local` and test the app against its dedicated local test database. Run `pnpm db:setup` separately when you want to prepare databases without starting development. See [local-postgres machine setup](../../packages/local-postgres/README.md#install-and-machine-setup) for the shared local service requirements.

To try it inside this repository, first run `./script/update` at the root, then copy `.env.example` to `.env.local` inside `examples/starter`, replace `BETTER_AUTH_SECRET` with the output of `openssl rand -base64 32`, and run `pnpm dev`. Keep the `workspace:*` dependencies for repository development.

The command initializes Git when it is available and the target is outside an existing repository, then runs `pnpm run setup` to install dependencies and Quality's pre-commit hook before staging the generated files and installed lockfile. The first commit runs the hook's lint and typecheck gates; a failed gate leaves it uncommitted. Pass `--no-git` to skip repository creation. Setup installs a hook only when the app has its own `.git`, so it leaves an enclosing repository's hooks alone. After cloning the generated repository, run `pnpm run setup` to install dependencies and the hook for that checkout. Run `pnpm ready` for the full local gate: lint, typecheck, build and tests. Run `pnpm lint` to check the shared Quality policy and `pnpm format` to apply its fixes and formatting. The starter's `biome.json` extends `@shivaedev/quality/biome`; no Quality config or baseline is needed. The included `.github/workflows/ci.yml` runs the same checks through `pnpm run ci` against a PostgreSQL service on pushes and pull requests.

To verify the generated app against published packages, run `pnpm --filter @shivaedev/starter check:published` at the root. The command creates temporary folders outside the workspace, installs the exact npm versions in `published-versions.json`, checks framework README imports, packs and installs `@shivaedev/create-app`, generates an app, then runs that app's Quality lint, typecheck, Vite build and PostgreSQL/authenticated HTTP round-trip tests. It uses the shared local test database prepared by `./script/update`; set `TEST_DATABASE_URL` to use another dedicated PostgreSQL database whose role can create disposable databases. Missing database access fails the check. Temporary copies are removed on completion or failure.

For changes awaiting a framework release, `pnpm ready` runs the same documentation and generated-app checks with verified workspace archives, adding tarball overrides only to the temporary consumers. Registry mode remains the release check against the pinned npm versions.

The starter passes queue definitions to effect-pg-boss's `NoteJobs.layer({ connectionString, jobs: [CountWords] })` to create its queues and dead-letter queues before serving requests, without starting a consumer. The separate worker registers the handler. The published-version check includes their PostgreSQL/live-update round trip.

Change the shared operations in `src/notes.ts`, the table and services in `src/server`, and the screen in `src/client`. The CSS declaration is local; no `vite/client` types are needed. `pnpm build && pnpm migrate && pnpm start` serves the built app on port 3000; run `pnpm worker` in a second process to handle jobs.

The notes route loads an authenticated RPC query; the create command is also protected. Missing or revoked sessions return typed `Unauthorized` failures that the UI presents as a sign-in prompt. Each account sees its own notes. `SessionBoundary` replaces the query registry and drafts when the session changes. Better Auth's HTTP endpoints share the app host at `/api/auth/*`; Vite proxies both auth and RPC to that host during development.

The starter uses strict application checking with `skipLibCheck: true`, matching Quality's application configuration. Better Auth's published declarations also reference runtimes this Node app does not use. Auth setup is local to `src/server/makeAuth.ts`; `src/server/migrations.ts` calls Better Auth's [programmatic migration API](https://better-auth.com/docs/concepts/database#programmatic-migrations), so no separate auth CLI step is needed. With `PUBLIC_URL` unset, auth supports the documented `127.0.0.1` HTTP development and built-app URLs.

## Add a job

Define a payload Schema with `defineQueue` in `src/server/noteJobs.ts`, and register its handler in `src/server/noteWorker.ts`; the worker uses the host's `appDatabase` Layer.
Register the queue definition in the request runtime's jobs Layer, then call `jobs.enqueue(queue, payload)` after the command's database transaction completes. Keep enqueueing independent of application SQL transactions and handle queue failures so a queue error cannot fail a note write. The starter logs failures and returns the saved note, leaving its word count pending when enqueueing fails.
After the worker writes, call `invalidateOnCommit` with the contract's invalidation keys; PostgreSQL delivers the hint to the server and the mounted live subscription refetches the query.

## Deploy

Enable Railway's per-service tracing setting separately for the web and worker services to supply the standard OpenTelemetry exporter variables. Both export their Effect spans through Effect's OTLP/HTTP JSON tracer. For another collector, set `OTEL_EXPORTER_OTLP_ENDPOINT` to its base URL (the exporter appends `/v1/traces`) or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` to its complete traces URL, which takes precedence. Set `OTEL_EXPORTER_OTLP_HEADERS` to comma-separated `key=value` headers with URL-encoded values, `OTEL_SERVICE_NAME` to the service identity, and optional `OTEL_RESOURCE_ATTRIBUTES` to comma-separated resource attributes. Without an endpoint, no exporter runs. eBPF auto-instrumentation is not part of the framework path.

### Railway with PostgreSQL

1. Push the generated repository to GitHub. Install the [Railway CLI](https://docs.railway.com/guides/cli) (5.42.1 or newer), run `railway login`, and create an empty project with `railway init` or link an empty project with `railway link`. Run these commands from the generated app's root, after `pnpm run setup` has installed its pinned `railway` TypeScript SDK.
2. In the Railway dashboard, add an empty service named `web`, keeping its source disconnected. Generate its public domain in Networking settings. In the selected environment's shared variables, create `BETTER_AUTH_SECRET` with the output of `openssl rand -base64 32` and `PUBLIC_URL` with that full HTTPS URL. Create both shared values before the first plan/apply; web references them through `ctx.shared` in the configuration.
3. Run `railway config plan`. The CLI evaluates `.railway/railway.ts`, reuses `web`, and previews a `Postgres` database and `worker` service. Review that plan, then run `railway config apply` and confirm it. The configuration uses the linked project's name, connects both services' `DATABASE_URL` to `Postgres`, and gives web references to the shared authentication secret and public URL. It sets `HOST=0.0.0.0` and `TRUSTED_PROXY=100.64.0.0/10` on `web`; Railway supplies `PORT`. The worker needs no public domain. Keep PostgreSQL's persistent volume and credentials in Railway.
4. Connect both services to the GitHub repository in their source settings, keeping the service root at the repository root, then deploy both. Railpack installs dependencies and runs `pnpm build`. Web runs `pnpm migrate` in its pre-deploy container to apply the numbered notes and Better Auth migrations and prepare pg-boss storage and queues. A failed migration stops the new web deployment while the old version keeps serving. Neither service migrates at boot. The worker fails startup until the schema is current; Railway restarts it on failure. The web service starts `pnpm start`, and Railway checks `GET /health` with a 120-second timeout before routing traffic. The worker starts `pnpm worker` without an HTTP health check.
5. Open the application domain, sign up and create a note. Confirm the word count appears, then sign out and back in to check the saved note. Change the secret or public URL in the environment's shared variables and redeploy web when either changes. Keep these values in shared variables rather than service-specific overrides; later plan/apply runs retain the references without putting the values in source.

After editing `.railway/railway.ts`, run `railway config plan` and `railway config apply` again. Railway deploys do not apply the TypeScript file automatically. Keep the file as the complete configuration for this project's environment; review any resource deletions in the plan before applying. See [Railway Infrastructure as Code](https://docs.railway.com/infrastructure-as-code) for the CLI workflow.

The server and worker use the same PostgreSQL database. Local `pnpm db:setup` is for development and must not run against the hosted database.

### Server environment

The worker and `pnpm migrate` need only `DATABASE_URL`, shared with web. Set these variables on web:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Your PostgreSQL connection URL. |
| `BETTER_AUTH_SECRET` | A random secret of at least 32 characters, kept in the host's secret settings. |
| `PUBLIC_URL` | Your public app URL, such as `https://app.example`. Its origin configures Better Auth's base URL, trusted origins and RPC session Origin policy. HTTPS enables secure cookies. Leave it unset for loopback HTTP development. |
| `PORT` | The port supplied by your host; defaults to `3000`. |
| `MAX_BODY_SIZE` | Maximum RPC request body size in bytes; defaults to `1048576` (1 MiB). |
| `HOST` | `0.0.0.0` to listen on the container's network interface; defaults to loopback. |
| `TRUSTED_PROXY` | A comma-separated list of proxy peer addresses or CIDR ranges, such as `10.0.0.0/24,2001:db8::/32`. IPv4, IPv6 and IPv4-mapped IPv6 peers are supported. The same peer matching controls forwarded RPC authority and Better Auth client IPs for rate limiting. Without it, the RPC guard retains its loopback default and auth ignores forwarded IP headers; production auth warns and uses one shared rate-limit bucket per path. |

For Railway, use `TRUSTED_PROXY=100.64.0.0/10`, the observed source range of its edge proxy. Railway does not promise this range, and it also trusts other services in the same Railway project; see [Railway's networking specs](https://docs.railway.com/networking/public-networking/specs-and-limits). A matching proxy peer must forward `X-Forwarded-Host` and `X-Forwarded-Proto` (`http` or `https`) for the public URL; any browser `Origin` must match that authority. It must also overwrite `X-Forwarded-For` with the client IP or append the actual client IP to the incoming chain. Better Auth resolves the first untrusted address from the right, skipping the configured trusted hops. Auth ignores `X-Forwarded-For` from peers outside `TRUSTED_PROXY`.

Use `GET /health` for the web service healthcheck. It queries PostgreSQL on each request, returns `200` only when the query succeeds within two seconds, and returns `503` when the database is unavailable or the probe times out. Both responses have an empty body, require no authentication and disable caching. Better Auth’s `/api/auth/ok` only checks the auth process.

Web’s pre-deploy step owns migrations. The `.railway/railway.ts` web configuration sets `preDeploy: "pnpm migrate"` to run migrations in a separate pre-deploy container before the new web version starts. A failed migration exits nonzero and stops that deployment; Railway keeps the previous version serving. The command also prepares pg-boss storage and producer queues; web and worker disable pg-boss’s schema migration at boot. The migration command needs only `DATABASE_URL`, and rerunning it preserves applied migrations and application rows.

Neither web nor worker runs migrations at boot. Both use `migrations.mode: "check"` to require the numbered migrations in their loader to be recorded in the shared ledger before initializing authentication, HTTP or jobs. This prevents web from initializing Better Auth while its `user`, `session`, `account` and `verification` tables are still missing. A worker started before pre-deploy finishes exits with a schema-not-current error; Railway’s restart policy starts it again until the schema is current. For local production runs, run `pnpm migrate` before `pnpm start` or `pnpm worker`; `pnpm dev` performs this step before starting watchers.

The worker logs `Worker migrations applied` after confirming that its required migrations are recorded, then `Worker ready to take jobs` after pg-boss registers its handlers. Both lines use Effect’s logger and include no connection details or secrets.
