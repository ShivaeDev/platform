# Commit-bound changes

Repository writes announce their own changes. A database-backed Platform host delivers them across processes through PostgreSQL NOTIFY, serves the subscription stream, and a React `SessionBoundary` mounts its bound contract APIs' live connections. An application declares query read keys and command invalidation keys; it needs no change channel option, subscribe operation or handler, `live()` call, or invalidation at repository write sites.

## Write and commit

`makeRepository` from `@shivaedev/sql/repository.ts` records the table name as the collection key and each written row's item key. Every written row keeps its record key, including in bulk writes. Fields marked with `bucket` from `@shivaedev/changes/buckets.ts` also announce their old and new bucket keys. Bucket writes use PostgreSQL 18 native `RETURNING old` values so conflict updates observe the stored row atomically. Insert, update, delete, void writes, conflict writes and the Many methods use rows returned by SQL, including generated IDs. Ignored conflicts and missing unversioned deletes announce nothing. Composite IDs use the JSON array of encoded primary-key values in `idColumn` order.

A repository write opens `transact` when called alone and joins the enclosing `transact` when several writes form one operation. The existing changes buffer deduplicates their keys. Its `BeforeCommit` hook sends NOTIFY through the writing connection, so PostgreSQL delivers the notification only after the outer commit and discards it on rollback. No trigger or second publisher is involved. Start enclosing transactions with `transact`, since a bare native transaction's commit cannot be observed by the change channel.

`migratePostgres` owns this boundary for its whole migration batch. Repository seed and upgrade writes announce after that batch commits and stay silent when it rolls back.

After a hosted command's handler returns, the host publishes its declared `invalidates(payload, result, viewer)` keys, excluding keys that the handler's repository commits already published. Remaining keys use a separate publication transaction and the same NOTIFY path. Keys that must commit atomically with a write come from the model's `bucket()` fields and the repository, rather than `invalidates`. The handler owns its transaction and error mapping; its after-transaction work keeps that boundary. A rejected command publishes no declared keys, while any repository transaction that actually committed still announces its writes.

Failed declared-key publication retries twice, after 50 ms and 100 ms, without repeating the handler. Exhausted retries preserve the committed result and mark local live streams for Resync, then attempt a broadcast Resync on the PostgreSQL change channel. The broadcast reconciles all listening hosts, including streams whose keys were not in the failed batch. If the channel is unreachable or rejects that broadcast, the server logs the delivery gap: a healthy remote listener can remain stale until a later reconnect, listener recovery or other reconciliation. NOTIFY has no durable replay.

Use `invalidateOnCommit` only for derived keys that neither a repository write nor the command declaration names. Ordinary SQL remains available for joins and exceptional writes, but raw writes must explicitly name their changes.

## Host and session defaults

`appDatabase` and database-backed `appHost` enable `postgresChanges` automatically. The default channel is `changes_` followed by the first 32 hexadecimal SHA-256 characters of `APP_NAME` or the database URL pathname, in that order. `config.applicationName` remains the PostgreSQL connection label and may differ between roles. Web hosts and workers must use the same name. `config.changes.channel` overrides the channel; heartbeat and retry settings remain optional.

Contracts include a framework subscription named `<contract>.$changes`. The host supplies its handler under the contract's middleware on Effect RPC's WebSocket transport. Each mounted bound query owns a cancellable subscription on the shared connection. The server registers its read scope before signaling readiness, then the client runs the ordinary authorized read once. Adding or dropping a query leaves other subscriptions and their values alone. The payload is `{ queries: [{ query: "get", payload: { id: 1 } }] }`, built from the declared query schemas. Changed hints rerun affected readers. Reconnect refreshes mounted queries because the host retains no offline key history.

A changed hint names the subscribed keys affected by an invalidation. Contract item reads register both `<collection>:<id>` and `<collection>:*`; a collection-wide invalidation produces a hint naming the subscribed item key. An item query should read its item key; add a list key when any write to the collection should refetch it. List reads still register only the table key. Code registering raw item Reactivity keys outside contract must also register the collection-wide key. Command invalidation keys are unchanged. Query handlers still enforce access policy and return authoritative data.

## Query read keys

Declare each query's dependencies with `reads(payload)`. For a query joining several tables, include each table's collection key so a write to either table refreshes it. Item keys give a narrower dependency when the query reads a specific row. Raw SQL and views need the same explicit declarations.

PostgreSQL's `pg_stat_xact_user_tables` scan counters cannot identify a query's dependencies from one snapshot at the end of a read-only transaction. On PostgreSQL 18.6 with `track_counts` enabled, `seq_scan` and `idx_scan` can retain reads from earlier committed transactions on the same connection until PostgreSQL flushes its pending statistics. Treating every positive counter as a dependency would subscribe later queries to tables they did not read. Read keys therefore come from the contract, with no extra SQL statement for automatic read tracking.

## Catch uncovered SQL in stories

The sql story kit exposes `withChangeCoverage(body, { covers }?)`, also exported from `@shivaedev/sql/testing.ts`. It runs the body inside `transact`, compares `pg_stat_xact_user_tables` counters before and after it, and requires every declared record and bucket key to have been recorded through `invalidateOnCommit`. Repositories declare their keys automatically. Raw SQL writers declare affected keys by table, for example `{ covers: { notes: [notes.item(id), notes.bucket.listId(oldList), notes.bucket.listId(newList)] } }`, including every bucket the row belongs to. A table name alone covers nothing. The check fails with `UnannouncedWrites` before commit and rolls back the body when declarations or recordings are missing. It checks declared keys rather than inspecting arbitrary SQL to infer affected rows; the raw writer remains responsible for complete declarations. PostgreSQL's transaction statistics retain writes from rolled-back savepoints, so those writes still need declarations.

The sql kit's `body.pipe(expectPublished(keys))`, also exported from `@shivaedev/sql/testing.ts`, observes `Published` events on the existing channel and compares distinct keys without regard to order. Wrap the committing body so the check sees publication after commit. Rolled-back keys do not count. `PublishedKeysMismatch` reports `expected` and `actual` keys in its fields and message. It preserves the body's result and existing delivery; an assertion failure after commit cannot undo the write.

For live delivery, use `watchHints(viewerStream)` from `@shivaedev/contract/testing.ts` to start a scoped subscription and await its first hint. `heard(viewer, keys, { within }?)` returns whether one delivered `Changed` hint contains all requested keys, including previously received hints. It waits up to one second by default using the story's Effect clock and returns `false` for unheard keys. Specs can assert allowed and denied viewers directly without support-code expectations or retry loops. The contract viewer kit exposes subscription setup as `listen(viewer, queries)` and the same `heard` verb.

## What the evidence covers

Commit-bound announcement is proved against real PostgreSQL: writes inside `transact` notify nothing before commit and one deduplicated key batch after it, for batches, conflict writes, ignored rows, outer rollback and discarded savepoints alike. Delivery between processes is proved against real PostgreSQL and real HTTP: a pg-boss worker's commit reaches a rendered client without application change wiring, a rolled-back worker write changes nothing, a command's declared keys are published exactly once, and a hint names only the changed subscribed item, so another item's query does not read again. The rendered client is a DOM fixture, so it does not prove SSR or browser lifecycle, and none of this establishes an application's deployment or durable delivery.

## Delivery limits

PostgreSQL NOTIFY is a wake-up signal, not a durable log. A heartbeat detects listener loss and resyncs live streams on loss and recovery. Payloads must be smaller than 8,000 bytes; the binding splits larger key batches and rejects a key that cannot fit before commit. A logical transaction therefore has one deduplicated batch, with multiple notifications only when its payload requires splitting. LISTEN requires a session connection; PgBouncer transaction pooling needs another adapter. Triggers, cascades and raw SQL remain invisible unless their keys are explicitly recorded; the coverage verb catches missing declarations and unrecorded declared keys in tests.

A listener outage logs one warning, `PostgreSQL change listener lost; resynchronizing live streams`, per process. Failed reconnect attempts log `PostgreSQL change listener reconnect failed; retrying` at debug without repeating the warning. Once the listener has re-subscribed, received its first heartbeat acknowledgement and resynchronized its streams, it logs one info line, `PostgreSQL change listener recovered; resynchronized live streams`. The recovery annotations are `downtimeMs` (milliseconds since the matching lost warning) and `streamCount` (the number of open live streams marked by that process's resync). Closed streams are excluded. Neither outage line includes a connection URL, credentials or the database error cause. A recovery line always follows a lost warning; the initial successful connection logs neither line. A lost warning without a subsequent recovery line means the listener is still retrying.

Listener recovery does not replay database operations. A request racing backend termination can fail with the application's mapped SQL error, including a read already executing on that backend. The native pool replaces failed connections for subsequent operations. Against real PostgreSQL with two HTTP servers and a pg-boss worker, an HTTP read waiting on a terminated backend fails with `Unavailable`, and after both servers report listener recovery, fresh reads, worker commits and cross-server change delivery succeed. The recovery log confirms the listener's subscription, heartbeat and resync; it does not guarantee that every concurrent operation succeeded.
